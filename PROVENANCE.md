# Provenance of every vendored file

**This file is the authority.** It is not documentation *about* the vendoring — it is the input the
vendoring tools read. `tools/provenance.py map` derives the per-file mapping from the tables below,
`tools/provenance.py headers --apply` (`just vendor-headers`) writes the headers from that mapping,
and `verification/check_drift.sh` (`just check-drift`) diffs every vendored file against the commit
named here and fails on any divergence this file does not enumerate.

Pins are **not** declared here. Every `anchor` column value is a key into [`pins.json`](pins.json),
which is the single source of truth for commits and versions (see [`PINS.md`](PINS.md)).

Vendoring requires an inventory justification, not a habit: every row carries an `inventory` column
naming its entry in [`REUSE-INVENTORY.md`](REUSE-INVENTORY.md), and
`verify_provenance_complete` fails if that entry does not exist.

> `reference/PROVENANCE.md` remains as the **narrative** companion for the `reference/` bundle —
> what each directory is, how stale it is, and what must not be trusted. It is prose for a reader.
> This file is the mapping a tool can execute.

## The provenance header

Every vendored file carries a header naming where it came from. The header is written by
`just vendor-headers` (`tools/provenance.py headers --apply`) and is the **only** edit the tools
make to a vendored file; `check-drift` strips it before comparing, so a header can never mask a
content change.

```
// BEGIN VENDORED-PROVENANCE — generated by `just vendor-headers` (tools/provenance.py); do not hand-edit.
// VENDORED — not our code. Re-vendor rather than editing here.
//   upstream-repo:   AztecProtocol/aztec-packages
//   upstream-path:   yarn-project/simulator/src/public/avm/avm_simulator.ts
//   upstream-commit: 3a68d68ac29aaf04fc6251c80a8eb874043cb260
//   licence:         Apache-2.0
//   local-edits:     none
//   inventory:       REUSE-INVENTORY.md RI-24
// END VENDORED-PROVENANCE
```

The `BEGIN`/`END` sentinels are what the stripper matches, so the header can be removed exactly and
re-added idempotently. A file that has **no** upstream counterpart — an `added` row in the recorded
edits below — gets a header that says `ADDED HERE — this file has NO upstream counterpart` and
`upstream-path: (none — added in this repo)`, because a header naming a path that does not exist
would be worse than no header at all.

`//` for `.ts` `.hpp` `.cpp` `.rs` `.nr` `.pil`, `#` for `.toml`, an HTML comment for `.md`, and a
JSX comment for `.mdx` (an HTML comment is a parse error in MDX v2). In a `.md`/`.mdx` file with
YAML frontmatter the header goes **after** the closing `---`, because docusaurus frontmatter must be
the first bytes of the file.

`local-edits:` is `none`, or the edit class from the table at the bottom of this file. That makes
the header the per-file half of the drift ledger: a file that says `none` must be byte-identical to
upstream once the header is stripped, and `check-drift` asserts exactly that.

## Derived trees

A tree listed here is not hand-maintained: it is **generated** from another tree by a recorded
transformation, and `check-drift` regenerates it into a scratch directory and requires byte
equality. This is what makes the transformation reproducible rather than a one-off `sed` whose
effect nobody can re-derive.

| local | derived from | transformation | why |
|---|---|---|---|
| drift/src | spike/src | `tools/provenance.py render-drift` (`just regen-drift`) | `drift/` is `spike/` against the `current` npm pin instead of the `deletion_era` one. The entire API drift across those eight weeks is one mechanical rename, `AztecAddress.from{Field,BigInt,Number,String}` → `from…Unsafe`. Recording it as a transformation means a future re-pin re-runs it instead of re-deriving it, and means the claim "that rename is the *entire* API drift" stays checkable: if a later nightly needs a second edit, regeneration fails and the second edit has to be recorded here. |
